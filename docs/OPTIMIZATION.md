# 优化诊断：这个项目真正的问题不在功能

体检日期 2026-10-22。所有数字来自实际测量，命令附在文末可复算。

---

## 结论先行

1. **系统从未被真正使用过。** 库里 25 条观测**全部来自种子数据**，真实观测为 0；
   7 条自主循环生成的提议无人处理。这不是功能问题，是产品问题。
2. **主指标选错了。** 「价值分」是一个自造标量，它的绝对值没有外部参照，
   唯一作用是被优化——这恰好是本项目自己在 `audit.py` 里警告过的 Goodhart 陷阱。
   而真正有独特价值的东西（预测校准）被放在了附录位置。
3. **继续加功能的边际收益已经为负。** 5700 行代码、87 项测试、21 个 CLI 子命令，
   但要回答「我这一年判断准不准」，仍然依赖用户每周手工输入 15 次。

### 输入成本的具体数字

按种子数据的采集周期算：

```
daily   × 1  →  7.00 次/周
weekly  × 6  →  6.00 次/周
monthly × 7  →  1.75 次/周
quarterly × 2 →  0.16 次/周
────────────────────────────
合计 约 14.9 次输入/周（按每次 40 秒约 10 分钟/周）
```

10 分钟不算多。**真正的问题不是时间，是打断**：每次都要先想起系统存在、
再想起指标 id、再打开终端。14.9 次上下文切换/周，实际结果就是 0 次。

## 二、四个真问题

### 1. 采集假设了「用户会持续主动输入」——这个假设已被证伪

设计上默认「人每周填 15 次」，实测 0 次。任何以「坚持记录」为前提的系统，
最终都会变成一份漂亮的空表。

### 2. 「价值分」是个自我指涉的指标

`value = Σ wᵢ·progressᵢ / Σ wᵢ`，其中 baseline 和 target 都是人拍的。
这个数的绝对值没有意义（0.292 是好还是差？无从判断），
它的变化也没有外部锚点（目标改了，分数就变了）。

项目自己在 `audit.py` 里专门检测「事后移动门柱」，却在主指标上依赖人拍的目标值——
这是内在矛盾。

而**校准**不一样：`p=0.7` 的预测有没有 70% 兑现，是**外部可检验**的，
不依赖任何人的自我评价。这才是这个系统唯一不可替代的部分。

### 3. 三块拼图各自为政

```
量化层（16 指标）      →  从未真实采集
模型层（Jev-1B）       →  未训练、实验阴性
Agent 层（12 工具）    →  跑在规则路由上
```

三层之间没有闭环：模型没被 agent 用上，感知层的结果没有喂给指标，
agent 提议的 7 条待办没人处理。它们共用同一个仓库，但没有共用同一条价值链。

### 4. 工程债已经在积累

- 无 git：5,700 行代码，任何一次误改都无法回滚
- 无备份：`~/.lifeplan/lifeplan.db` 是单点故障，没有导出/恢复演练
- 进度计算散在 4 处：改一处公式要记得改另外三处
- 9 个公开函数无人调用：`suggested_p_hit`、`calibration_health`、
  `overdue_days`、`write_dashboard`、`db.scalar`、`autopilot.pending` 等 —— 
  写的时候以为会用，实际没用

## 三、三条可选路线

| 路线 | 做法 | 成本 | 能解决什么 | 风险 |
|---|---|---|---|---|
| A 继续加功能 | 更多指标、更多报告、更多工具 | 中 | 几乎没有 | 代码继续膨胀，使用率仍是 0 |
| B 自动化采集 | 从 git / 文件 / 进程推断指标值 | 中高 | 覆盖约 30% 指标（提交数、活跃度） | 睡眠、面试、关系这类**根本推不出来**；推断错了会污染台账 |
| C 改变输入单位 | 从「每个指标填一次」改为「每周一次批量复盘」 | 低 | 直接解决打断问题 | 需要放弃「全指标覆盖」的执念 |

### 我的判断：走 C，把 A 和 B 降为辅助

理由很直接：B 的覆盖面上限就是硬约束。你把 16 个指标摊开看——
睡眠、深度对话、面试转化、储蓄——**一半以上只能靠人报**（人报 = tier1 自述）。
既然自动化救不了，就必须降低「必须由人报」的次数，而不是让每次报得更快。

**把交互单位从「指标」改成「周」**：一周只被打断一次，一次处理完所有到期项。

同时做一件反直觉的事：**把「价值分」从主指标降为参考，把校准证据升为主指标。**
理由见问题 2——只有校准的判据在系统外部。

## 四、优先级路线

### P0（立刻，1 次会话内）

1. **`lifeplan week`**：一条命令跑完一周复盘——到期预测逐个结算、
   过期指标逐个补录（带建议值，回车即接受）、无观测指标可归档。
   目标：把 14.9 次打断压成 1 次、3 分钟内。
2. **`git init` + 首次提交**：5,700 行代码不能没有历史。
3. **`lifeplan backup / restore`**：单文件数据库必须有可验证的备份恢复路径。

### P1（下一轮）

4. **报告改版**：首页从「价值分」换成「校准摘要」（Brier、ECE、偏差趋势、样本量）。
   价值分挪到第二页，并明确标注「自造标量，仅供内部比较」。
5. **进度公式收归一处**：`metrics.goal_progress()` 成为唯一入口，`audit.py` 改为调用它。
6. **清理 9 个未使用函数**：要么接进流程，要么删掉。

### P2（有模型之后）

7. 接一个本地 3B（Ollama）驱动 agent，把 agent 从「问答」升级为「每周复盘助手」：
   读本周数据 → 生成 3 条该押的预测 → 下周结算。
8. **Jev-1B 建议封存**：实验结论为阴性，从零训练 20B token 需约 260 GPU·h，
   而同等成本直接用一个现成 3B 效果更好。保留为「方法与核算」的技术文档，
   不再追加训练投入。

## 五、怎么判断优化有效

优化不能靠感觉。定三个可测的验收标准：

| 指标 | 现状 | 4 周后目标 |
|---|---|---|
| 每周实际交互次数 | 0 | 1 次（且完成） |
| 已结算预测累计 | 8（种子） | ≥ 20（达到校准最低样本量） |
| 校准误差 ECE | 0.4438 | < 0.20 |

第三条尤其重要：**ECE 下降是这个系统唯一能自证的「有用」**。
如果 20 条真实预测之后 ECE 没有下降，说明连校准这条路也没走通，
那时应该承认这个方向的局限，而不是继续加功能。

## 六、明确不做

## 七、本轮已执行（含首次真实使用的实测）

### 7.1 `lifeplan week`

交互单位从「指标」改成「周」。一次跑完：到期预测逐个结算、过期指标逐个补录
（可自动推断的给出建议值）、反复记不上的指标当场归档。

首次真实跑（9 项，约 2 分钟）：

```
✓ 已结算预测 2 条、补记观测 4 条、归档指标 1 个、跳过 2 项
  当前校准：Brier 0.2270，ECE 0.3800，过度自信 +0.1600（n=10）
  系统性过度自信：说'能做到'时更容易做不到
```

自动建议生效过一次：扫描本机 git 仓库近 7 天的提交数，
直接作为「月度有效提交数」的建议值，回车即接受。

### 7.2 这次实测暴露了一个更重要的问题

填完一周数据后，**价值分从 0.292 跳到 0.725**。

不是因为生活变好了，而是因为：实际提交量把 `target=12` 的指标直接打满。
而 `target=12` 是我当初随手填的。

这实证了第 2 条诊断：**baseline/target 是人拍的，所以价值分不可解读**。
同一个人的同一周，分数从 0.29 到 0.73，只取决于当初谁写了 target。

结论不变、但更强了：**价值分只能内部纵向比较，不能当作"我过得好不好"的读数**。
主指标必须换成校准——它的判据（预测兑现率）在系统外部，改不了。

### 7.3 备份与恢复（已演练）

### 8.1 进度公式收归时发现的一个真 bug

`audit.py` 里那份内联副本**漏了 `maintain` 分支**。对"维持型"指标
（日均睡眠 7h 这类），它按 `increase` 计算，得到负分——
也就是说审计模块过去会把"睡眠正常"判定为"进展为负"。

统一到 `goal_progress()` 后，三条分支（increase / decrease / maintain）只有一处实现，
并加了回归测试：用 maintain 主指标 + maintain 代理指标构造场景，确认不再误报代理反噬。

### 8.2 报告与看板的新顺序

```
一、校准摘要（主指标）   ← Brier / ECE / 过度自信 / 可靠性分箱 / 分领域偏差
二、计划状态（参考）     ← 明确标注「自造标量，不可当过得好不好的读数」
三、分领域
四、目标明细
五、承诺与产能
六、不可量化登记
七、自我审计
附、宿主画像
```

看板的 KPI 也从「价值分 / 置信度 / 覆盖率 / Brier / ECE / 过期」改为
「Brier / ECE / 过度自信 / 已结算 / 覆盖率 / 价值分（参考）」。

新增的可靠性分箱表比总分有用得多，例如本轮数据直接显示：

| 预测区间 | n | 平均预测 | 实际命中 | 偏差 |
|---|---|---|---|---|
| 0.5–0.6 | 3 | 0.53 | 0.00 | −0.53 |
| 0.7–0.8 | 3 | 0.70 | 0.33 | −0.37 |
| 0.8–0.9 | 2 | 0.82 | 1.00 | +0.18 |

「说到五成把握的事，一件都没做到」——这条信息在原来的总分里完全看不见。

### 8.3 顺带修掉的健壮性问题

- **看板在白屏边缘**：原实现直接 `{cal.brier:.4f}`，没有已结算预测时 brier 是 `None`，
  会抛 TypeError 导致整个看板生成失败。新库上必然踩到。已改为 `—`。
- **`ensure_schema` 漏了 `meta` 表**：老库打不开体检命令。
- **种子数据未标记**：`doctor` 曾把 25 条种子观测报成"真实观测"。
  现在 seed 时写入 `meta.seeded_at`，体检会明确提示"计数包含演示记录"。

验收口径不变：**4 周后 ECE 是否从 0.38 降到 0.20 以下**。
如果不降，说明连校准这条路也没走通，那时该承认局限，而不是继续加功能。
